Whiteboard it in five minutes

Every system-design round starts the same way: “walk me through something you built.” This is the version that survives follow-up questions.

The 90-second opener

Lead with the problem shape, not the tech list. Naming Kafka in sentence one invites “why Kafka?” before you have earned the right to answer it.

🎙️
Say this

“An e-commerce checkout where placing an order has to reserve stock and take payment — two writes that live in different services with different databases. There is no distributed transaction, so the interesting problem is: how do you keep those consistent when the second step fails? I solved it with a choreographed saga plus compensating actions, and the hard parts were exactly-once semantics, concurrent stock reservation, and knowing whether it actually worked in production.”

That paragraph plants three flags an interviewer can pull on — saga, concurrency, observability — and every one of them is a topic you have real code for.

The follow-up you will get, and the answer that lands

Q
“Why microservices for a shop?” The honest answer scores higher than the enthusiastic one: “For a real shop of this size, I would not. This was built to exercise the pattern. What the split genuinely buys is failure isolation — email being down cannot fail checkout — and a hard security boundary, because Payment has no credentials for the customer table. What it costs is that nothing is instantaneous and one request leaves footprints in five services.”
Q
“Why not two-phase commit?” “2PC needs a coordinator holding locks across services for the length of the slowest participant, and any participant that dies in the prepared state blocks the others. Payment can take seconds. I traded atomicity for availability and accepted eventual consistency with compensating actions.”
Q
“Where is the single point of failure?” “The gateway, deliberately — it is the only reachable entry point, which is what makes verified identity headers trustworthy downstream. In this shape it is one process with a circuit breaker per upstream; in production it would be horizontally scaled behind a load balancer, which it can be because it holds no state beyond a TTL-cached permissions snapshot.” That property — no per-request state — is what makes it horizontally scalable.

The one snippet worth memorising

If they ask “show me the most important twenty lines,” this is the write that makes the whole design hold together.

CODE 
  await tx.enqueue(ORDER_PLACED, orderId, {
    orderId,
    userId: p.userId,
    items: p.items.map((i) => ({ productId: i.productId, quantity: i.quantity })),
  });
  return { outcome: "PLACED", orderId };
WHAT TO SAY ABOUT IT

“The event is written as a row, inside the same transaction as the order.” That single decision removes the dual-write problem — Module 3.

“It carries the ids, not the prices.” Order priced the line itself from its own read model; sending a price would let a consumer disagree about money.

“tx is a port, not Prisma.” The domain function takes an interface, so the business rule is unit-testable with no database — the same shape as the state machine.

Expect: “what publishes it, then?” A polling relay with publisher confirms, marking rows sent only after the broker acknowledges.

services/order/src/place-order.ts 47 lines. Read it before any interview where you plan to mention this project.

Numbers to have ready

Vague answers read as second-hand. These are measured, not estimated — Module 6 covers how.

saga p99 < 5s The end-to-end SLO, enforced as a k6 threshold, not a hope.
http p95 < 500ms Edge latency for synchronous calls.
10 / min Rate limit on /auth/*. 300/min everywhere else.
15m / 7d Access-token and refresh-token lifetimes.
6 invariants Checked across 7 databases and both brokers by a script that exits non-zero.
