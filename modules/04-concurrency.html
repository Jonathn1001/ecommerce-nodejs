Module 4

Read-then-write, and the bugs it hides

One shape causes most “impossible” production bugs. Interviewers probe for it because it is invisible under low load and inevitable under high.

The shape

1
Read a value.
2
Decide something based on it.
3
Write the result back.

Two copies running at once both complete step 1 before either reaches step 3. Both decide against the same stale value. Engineers call the window between the check and the act TOCTOU.

🎰
Why it survives testing

Under test there is one request at a time, so the window never opens. It appears first in production, at the worst moment — a flash sale, a retry storm — and presents as data that “cannot happen”: negative stock, two payments, two live tokens in one family.

Three fixes, and when each is right

🔐

Compare-and-set

UPDATE … WHERE status = <what I read>. Zero rows affected means you lost the race. Best when losing is legitimate and should be a silent no-op — exactly the saga case.

🔒

Pessimistic row lock

SELECT … FOR UPDATE serialises the readers. Best when contention is high and retrying is expensive — stock, balances, counters.

🧬

Atomic upsert with a version guard

ON CONFLICT DO UPDATE … WHERE EXCLUDED.version > version. One statement, no read at all. Best for projections applying out-of-order events.

🗣️
Say the isolation level out loud

“Postgres defaults to READ COMMITTED, so two transactions can both read the same row and neither sees the other until commit. SERIALIZABLE would catch it, but it costs retries under contention — I preferred a targeted CAS to a global isolation change.” That sentence tells an interviewer you know the tradeoff exists.

CAS, in the saga

CODE 
  // Compare-and-set: `expected` is the status we read above. A lost CAS means another
  // event legitimately advanced this order, so this one must emit nothing.
  const moved = await tx.setStatus(p.orderId, next, order.status);
  if (!moved) return "NO_OP";
WHAT TO SAY ABOUT IT

“The third argument is the guard.” The write only lands if the row still holds the status we based our decision on.

“Losing is not an error.” It means another event advanced the order first, legitimately — so we emit nothing rather than retrying, which would double-emit.

The follow-up: “is this reachable?” Honest answer: not today, because Payment emits one deterministic result per order and one consumer group processes a partition serially. It is defence against a future second producer — and I would rather have it than discover the gap during an incident.

The sharpest example: claim before you mint

Refresh-token rotation. Two concurrent rotations of the same token both read revokedAt === null. Without a claim, both mint — and a thief racing the honest client never trips reuse detection.

CODE 
  // Claim the row FIRST. Under READ COMMITTED two concurrent rotations of the same token
  // both read revokedAt === null; whichever revoke commits second matches zero rows. Without
  // this check both would mint, leaving two live tokens in one family — and a thief racing
  // the honest client would never trip reuse-detection, which is the whole point of the
  // mechanism. The loser rolls back (the caller throws) and gets a 401.
  const claimed = await tx.revokeOne(row.id, now, true);
  if (claimed === 0) return { outcome: "RACE", userId: row.userId };
WHY THIS IS AN INTERVIEW ANSWER

It is a race with a security consequence, not just a data one. That distinction is what makes it memorable to an interviewer.

The order of operations carries the whole fix: revoke first, mint second. Reversed, the mechanism silently stops detecting theft while every test still passes.

The return value is the race detector. revokeOne returns rows affected — zero means someone else claimed it, so this caller must fail rather than proceed.

Volunteer the tradeoff: a 10-second grace window treats an honest double-submit from two tabs as legitimate instead of logging the real user out. It deliberately narrows detection by ten seconds.
