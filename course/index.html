Inside a Distributed Checkout
Module 1

One click. Seven programs.

This project is an online store. You browse products, add one to a cart, and click Place order. That is the whole product.

What makes it worth studying is what happens after the click. The store is not one program — it is seven services, running side by side, each owning one job and none of them able to see the others’ data.

Where the click actually lands

Here is the real code that ends the first step. It is short on purpose — writing the order and announcing it happen together.

CODE

Which order it was about.

Who placed it — Inventory and Payment will both need this later.

What was in it: product ids and how many. Not prices — Order decides those itself.

The word to steal: outbox

The announcement is written into the same database as the order, in the same all-or-nothing write. A separate loop mails it out afterwards. That is why an order can never exist without its announcement — and why saying “use the outbox pattern” to an AI gets you something durable instead of something hopeful.

Module 2

The cast, and why there are seven of them

Cutting one program into seven is not free. Here is what each one owns — and what the split actually buys you.

Think of a hospital, not a factory

A hospital does not have one person who does everything slightly. It has a radiology department, a pharmacy, a records office. Each holds its own equipment and its own files, and no department rummages through another’s cabinets.

That is this system. The rule that makes it real: each service owns its own database, and nobody else may read it. Engineers call the door in front of them a gateway.

What the split buys, and what it costs

✅

Buys: blast radius

Email is down? Orders still complete. In one big program, a crash in the email code takes checkout with it.

🔒

Buys: a real boundary

Payment cannot read customer emails because it has no access to that table. Not “should not” — cannot.

🐌

Costs: nothing is instant

A fact announced by one service arrives at another a moment later. Code that assumes “it is there now” will be wrong sometimes.

🔍

Costs: harder to follow

One checkout leaves footprints in five programs. That is why this project spends real effort on tracing — Module 5.

⚠️
Do not copy this shape by default

Seven services for a shop is deliberate overkill — this repo exists to teach the pattern. For most projects, one program is the right answer until it demonstrably is not. Being able to say that out loud is worth more than being able to draw the diagram.

Module 3

Three pipes, and knowing which one to use

Seven services, no shared database. Everything they know about each other arrives through one of three channels — and picking the wrong one is a design mistake you can learn to spot.

A noticeboard, a work tray, and a phone call

📌

Kafka — the noticeboard

You pin up a fact: “order 41 was placed.” Anyone may read it, now or in an hour, and reading it does not take it down. You never learn who read it.

📥

RabbitMQ — the work tray

You drop in a job: “charge $13.00.” Exactly one worker picks it up, and it disappears from the tray. A job nobody can do goes in the dead-letter queue.

📞

HTTP — the phone call

You ask and wait for the answer. Used only at the edge, between your browser and the gateway — this is the plain HTTP everything on the web runs on, because waiting is exactly what you want when a human is watching.

💡
The tell

A fact in the past tense — “payment succeeded” — goes on the noticeboard. An instruction — “charge this card” — goes in the work tray. Notice the past tense in the announcement and the imperative in the job. That grammar is the design rule.

Two readers, one announcement

“Order confirmed” was read by both Notification and Inventory, and neither knew about the other. Adding a third reader later — analytics, say — requires no change to Order at all. That is the payoff for the noticeboard.

One outbox, two destinations

Announcements and jobs are written to the same table. A single loop reads it and decides where each row belongs, purely from its type.

CODE 
    // Atomic command emission: the ChargePayment outbox row commits with the
    // status change; the relay routes it to RabbitMQ payment.charge.
    await tx.enqueue(CHARGE_PAYMENT, p.orderId, {
      orderId: p.orderId,
      userId: order.userId,
      amount: order.totalPrice,
    });
PLAIN ENGLISH

The comment is the design: this job is written in the same all-or-nothing write as the status change.

So an order can never be “awaiting payment” with no charge job queued, or vice versa.

Write a job row of type CHARGE_PAYMENT. The type is the only thing that decides it goes to the work tray rather than the noticeboard.

Which order to charge for.

Who is paying — Payment needs this to check the charge belongs to the right person.

How much, in whole cents. Never a decimal — money in decimals is how rounding bugs are born.

Module 4

There is no undo button

Stock is reserved in one database. Money is charged in another. When the money fails, nothing can roll both back together — so the system does something else instead.

Climbing with ropes, not with a safety net

Inside one database you get a transaction: all-or-nothing, and the database rewinds for you if anything fails.

Across five databases, no such rewind exists. So the checkout is climbed like a multi-pitch route: each step is anchored before the next begins, and if a later pitch fails you climb back down through the anchors you set — deliberately, one at a time. That descent has a name: compensation.

🧗
The word to steal: saga

A sequence of local steps, each with a matching undo-step, that together behave almost like one transaction. Saying “model this as a saga with compensating actions” tells an AI assistant far more than “make sure it rolls back” — because across services, rolling back is not a thing that exists.

The whole checkout, in eleven lines

This is the rulebook. Every state the order can be in, and the only events that may move it — the entire business process, small enough to read in one breath.

CODE 
  if (current === "PENDING" && eventType === INVENTORY_RESERVED)
    return "AWAITING_PAYMENT";
  if (current === "PENDING" && eventType === INVENTORY_RESERVATION_FAILED)
    return "CANCELLED";
  if (current === "AWAITING_PAYMENT" && eventType === PAYMENT_SUCCEEDED)
    return "CONFIRMED";
  if (current === "AWAITING_PAYMENT" && eventType === PAYMENT_FAILED) return "CANCELLED";
  return null;
PLAIN ENGLISH

If we are waiting to reserve stock and the stock got reserved…

…then move to awaiting payment. This line is why a status can prove a fact: there is no other way in.

If we are waiting to reserve stock and the reservation failed…

…cancel. Nothing was charged, so there is nothing to undo.

If we are awaiting payment and the money went through…

…confirmed. Done.

If we are awaiting payment and the card was declined, cancel — and that cancellation is what tells Inventory to release the stock.

Anything else: null, meaning “this event does not apply here.” A late duplicate changes nothing instead of corrupting the order.

Why that last line matters more than it looks

🔁

Messages arrive twice

Networks retry. A “payment succeeded” can genuinely be delivered two times — that is normal, not a bug to be fixed upstream.

🛑

The second one changes nothing

The order is already CONFIRMED, so the rulebook has no matching line and returns null. No double confirmation, no second email.

🧮

The word for it

Idempotent. Ask for it by name and you will get systems that survive retries.

Module 5

The small machinery that stops it rotting

None of these are features. Nobody asks for them. Without them the system slowly tells lies — and every one has a name worth knowing.

Five safeguards

📮

Outbox

Announcements are written into the service’s own table in its own database with the change they describe, then mailed out by a loop. Without it, a crash between “saved” and “announced” loses the announcement forever.

🧾

Processed ledger

Each service writes down every message id it has handled. A redelivery is recognised and dropped — the receipt drawer that makes retries safe.

🔐

Compare-and-set

“Change the status to CONFIRMED only if it is still AWAITING_PAYMENT.” Two events racing cannot both win.

🔌

Circuit breaker

After enough failures the fail-fast rule kicks in and the gateway stops calling a sick service and fails fast instead — like a fuse. Hammering something that is down makes outages longer.

📡

Server-sent events

One long-lived connection the server writes into as the order changes. That is why the tracker moves with no refresh and no polling.

Compare-and-set, in three lines

The most quietly important lines in the checkout. Read the comment first — the author is explaining a race to you.

CODE 
  // Compare-and-set: `expected` is the status we read above. A lost CAS means another
  // event legitimately advanced this order, so this one must emit nothing.
  const moved = await tx.setStatus(p.orderId, next, order.status);
  if (!moved) return "NO_OP";
PLAIN ENGLISH

A note to the next reader: this is a compare-and-set, and here is why it exists.

Losing the race is not an error — it means someone else moved the order first, legitimately.

Try to move the order to the new status, but only if it is still on the status we read a moment ago. The database checks and writes in one indivisible step.

If the status had already moved, do nothing at all — no announcement, no email, no second charge. Say “no operation” and stop.

🎯
Read-then-write is where bugs live

Any time code reads a value, decides something, then writes it back, two copies running at once can both read the old value. This is the single most common source of “impossible” bugs in busy systems. The phrase to use with an AI assistant is “make this a compare-and-set” or “take a row lock.”

Why the tracker moves on its own

The order page does not poll. The browser opens one connection and the server writes into it every time the order changes.

    } catch {
      return;
    }
PLAIN ENGLISH

Prepare a slot for whatever arrives, admitting we do not yet know its shape.

Try to read it as structured data…

…because it arrives as plain text and has to be converted.

If that fails — a truncated or malformed message —

And when the live connection dies?

It will. Tokens expire, networks drop, proxies interfere. The storefront climbs down a ladder rather than retrying forever.

1
First failure — refresh and reconnect. The likeliest cause is an expired sign-in, and that is the one thing the browser can fix by itself.
2
Third failure — give up on live, start asking. Close the connection and ask for the order every three seconds instead. Slower, but it works through proxies that block streaming.
3
Order settled — stop everything. A confirmed or cancelled order never changes again, so continuing to ask would be pure waste.
⚠️
Never run both at once

If the page asked every three seconds and kept the live connection, the tracker would still look perfect while streaming was completely broken — and nobody would find out for months. Redundancy that hides a failure is not redundancy.

Module 6

Five real bugs, and what they all had in common

These are not invented examples. Each one happened in this repository, and every single one passed the tests.

A green test suite is not evidence

Tests check what someone thought to check. These five bugs each lived in the gap between “the code is correct” and “the thing actually works when a person uses it.”

🌑
The app shipped permanently dark. A styling rule nested inside a “if the user prefers dark mode” block was silently moved to the top by the build tool, so the dark colours overwrote the light ones for everybody. Every test passed — no test looks at colour.
📄
Refreshing a product page returned raw data instead of the page. The web address for the product page and the address for the product data were the same, and the data won. Clicking around worked; pressing F5 did not. The test suite only ever clicked.
🕵️
Tracing was completely dead. The check for “is tracing switched on?” was fooled by how the program restarts itself, so the part doing the real work always skipped it. Six tests were written for it. All six passed against a system that recorded nothing.
📦
A new feature 404’d with correct code. The running container had been built before the feature existed. The code was right, the test passed, the running program was six hours old.
🧊
The live tracker froze in production only. The web server in front of the app — a proxy — was collecting the live updates and holding them until the end, which for a live stream is forever. Locally, with no such server in front, everything looked perfect.

Spot the one that freezes the tracker

Real configuration for the web server that sits in front of the app in production. One line is missing, and its absence is what froze the tracker. Click the line that needs a companion.

Which line is incomplete?

1 location /api/ {
2 proxy_pass http://gateway:8000/;
3 proxy_http_version 1.1;
4 proxy_set_header Host $host;
5 }
🔧
The missing line

proxy_buffering off; — by default this server gathers a response and forwards it in chunks, which is sensible for a web page and fatal for a live stream. The fix is one line; finding it took a browser and a production-shaped build.

The bug that could have passed forever

The server labels each live update status. Browsers deliver a labelled message only to a listener asking for that label — the generic “any message” handler never fires.

CODE — CORRECT 
  // NAMED event. The service writes `event: status`, and EventSource routes a named event ONLY
  // to a matching addEventListener — `onmessage` would never fire.
  es.addEventListener("status", (e) => {
WHY IT IS WRITTEN DOWN

The comment exists because the wrong version is the obvious one to write.

Had the test been built around the generic handler, every test would have passed against a page that received nothing at all.

So the fix came with a check: swap the label for the generic handler on purpose, and confirm a test turns red. A test that cannot fail is not a test.

🧪
The habit worth stealing: break it on purpose

After an AI writes a test for you, delete the line it is supposed to be testing and run it again. If it still passes, the test is decoration. This one habit catches more fake safety than any amount of reading.

A debugging order of operations

1
Is the running thing the thing you wrote? Rebuild and restart before debugging anything. Hours die here.
2
Which side of the door? Rejected before it reaches a service means gateway — identity, permissions, rate limits. Wrong data coming back means the service behind it.
3
Is anything stuck in a queue? A dead-letter queue filling up names the failing step precisely, and orders frozen part-way through tell you which service stopped listening.
4
Does it break only in the packaged build? Then suspect what is different about that shape: the server in front, the built stylesheet, the environment settings — not the logic.

What you can now say out loud

choreography Parts react to announcements; no conductor. The opposite is orchestration.
saga A sequence of local steps, each with an undo-step, standing in for a transaction that cannot exist.
compensating action The undo-step: release the stock, refund the charge.
outbox pattern Write the announcement with the change, mail it out afterwards.
idempotent Doing it twice is the same as doing it once.
compare-and-set Change it only if it still holds the value I read.
circuit breaker Stop calling something that is down; fail fast instead.
dead-letter queue Where unprocessable jobs are parked for a human.
server-sent events One connection the server writes into as things change.
eventual consistency Everyone agrees in a moment — not this instant. Design for the gap.

The one habit

Every serious bug in this project was found by running the thing — in a browser, in the packaged build, against a real database. Not by reading, and not by a green test suite. Build it, then go and use it.
