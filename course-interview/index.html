The follow-up you will get, and the answer that lands

Q
“Why microservices for a shop?” The honest answer scores higher than the enthusiastic one: “For a real shop of this size, I would not. This was built to exercise the pattern. What the split genuinely buys is failure isolation — email being down cannot fail checkout — and a hard security boundary, because Payment has no credentials for the customer table. What it costs is that nothing is instantaneous and one request leaves footprints in five services.”
Q
“Why not two-phase commit?” “2PC needs a coordinator holding locks across services for the length of the slowest participant, and any participant that dies in the prepared state blocks the others. Payment can take seconds. I traded atomicity for availability and accepted eventual consistency with compensating actions.”
Q
“Where is the single point of failure?” “The gateway, deliberately — it is the only reachable entry point, which is what makes verified identity headers trustworthy downstream. In this shape it is one process with a circuit breaker per upstream; in production it would be horizontally scaled behind a load balancer, which it can be because it holds no state beyond a TTL-cached permissions snapshot.” That property — no per-request state — is what makes it horizontally scalable.

Module 2

Consistency without a transaction

The saga question has a shallow answer everyone gives and a deep one almost nobody does. The deep one is about who owns the state machine.

Choreography vs orchestration — pick a side and defend it

💃

Choreography — what this system does

Each service reacts to events. Buys: no central bottleneck; adding a consumer needs no change upstream. Costs: the process exists in nobody’s code — you reconstruct it from traces.

🎼

Orchestration

One coordinator calls each step. Buys: the workflow is readable in one file, timeouts and retries are centralised. Costs: the coordinator becomes a dependency of everything and a deployment bottleneck.

🎯
The nuance that scores

“I chose choreography, but Order is still effectively the coordinator — because it owns the state machine. Every service emits facts; only Order decides what a fact means for the order. That is the middle ground: distributed execution, centralised interpretation. Pure choreography, where each service also infers its own view of the process, is where these systems become unreasonable.”

The state machine, and why it is eleven lines

Interviewers love asking “where does the business process live?” Point at one pure function with no I/O in it.

CODE 
  if (current === "PENDING" && eventType === INVENTORY_RESERVED)
    return "AWAITING_PAYMENT";
  if (current === "PENDING" && eventType === INVENTORY_RESERVATION_FAILED)
    return "CANCELLED";
  if (current === "AWAITING_PAYMENT" && eventType === PAYMENT_SUCCEEDED)
    return "CONFIRMED";
  if (current === "AWAITING_PAYMENT" && eventType === PAYMENT_FAILED) return "CANCELLED";
  return null;
WHAT TO SAY ABOUT IT

“It is a transition table keyed on (current state, event).” Not scattered ifs across consumers — one function, zero dependencies, trivially unit-testable.

“Illegal transitions return null.” A late or duplicate event finds no matching row and becomes a no-op instead of corrupting state — idempotency by construction, not by a flag.

“And the table doubles as a proof.” AWAITING_PAYMENT is reachable only via INVENTORY_RESERVED, so the status itself is evidence the reservation succeeded. The storefront tracker renders four saga steps from four statuses because of exactly this.

Follow-up they will ask: “what about a compensating event arriving out of order?” — the guard on current is what makes that safe.

services/order/src/transition.ts Pure domain core over a tx port — no Prisma, no config, no broker.

Compensation is not rollback — say it in those words

1
A rollback un-happens a change. Only a database can do that, and only within its own boundary.
2
A compensation is a new, opposite action — release the reservation, refund the charge. It is visible, it takes time, and it can itself fail.
3
So every forward step needs its inverse designed at the same time. “What is the compensating action?” is the question to ask about any new saga step — including in the interview, out loud.
4
Some steps have no inverse. An email cannot be unsent. Those belong at the END of a saga, after the last thing that can fail — which is exactly why Notification consumes order.confirmed and nothing waits on it.

Module 3

Delivery semantics, and the dual-write problem

“How do you guarantee the message gets sent?” is a trick question. The honest answer starts by rejecting the premise.

The dual-write problem, stated properly

You must save a row and publish an event. Two systems, no shared transaction. Whichever you do first has a window where the other fails.

💀

Save, then publish

Crash in between: the order exists and nobody downstream ever hears about it. Silent, permanent, and invisible until a customer complains.

👻

Publish, then save

Crash in between: consumers act on an order that does not exist. Stock reserved for a phantom.

📮

Transactional outbox

Write the event as a row in the same transaction as the order. A relay polls the table and publishes. Now there is one write, and delivery becomes a retry problem instead of a correctness problem.

🎯
The sentence to memorise

“The outbox converts an atomicity problem, which is unsolvable across two systems, into a delivery problem, which retries solve. The cost is at-least-once semantics and a polling delay — so every consumer has to be idempotent, which they need to be anyway.”

One outbox, two transports — the routing is the design

CODE 
    // Atomic command emission: the ChargePayment outbox row commits with the
    // status change; the relay routes it to RabbitMQ payment.charge.
    await tx.enqueue(CHARGE_PAYMENT, p.orderId, {
      orderId: p.orderId,
      userId: order.userId,
      amount: order.totalPrice,
    });
WHAT TO SAY ABOUT IT

“One outbox table, two destinations, routed purely by row type.” Commands go to RabbitMQ, events to Kafka. No second table, no migration to add a transport.

“The command commits with the state change.” An order cannot be AWAITING_PAYMENT with no charge queued, or vice versa — the classic partial-failure bug, closed by construction.

“The relay uses publisher confirms.” It marks a row sent only after the broker acknowledges, so a lost publish is retried rather than silently dropped.

“And the two lanes are isolated.” A Rabbit outage must not stop Kafka publishing — the tick settles both independently and catches per-lane errors.

Kafka or RabbitMQ — the answer is about the message, not the tool

Kafka (event log)
RabbitMQ (work queue)

“payment.succeeded” — a fact, past tense, multiple independent readers, replayable from an offset

Drop here

“ChargePayment” — an instruction, one worker must do it exactly once, needs a DLQ when it cannot be done

Drop here
consumer group Kafka fan-out unit. Order’s catalog projection runs in a separate group from its saga consumer, so one lagging does not stall the other.
partition key Ordering is guaranteed per partition only. Keying by orderId keeps one order’s events in sequence; there is no global order and you should say so.
prefetch RabbitMQ back-pressure — cap unacked messages per consumer (10 here) or one slow worker buffers the whole queue into memory.
DLQ Where poison messages park after bounded retries, instead of blocking the queue or vanishing.

“Do you have exactly-once?”

⚠️
Never answer yes

“No — nobody does, end to end. Kafka’s exactly-once applies within Kafka, to a read-process-write inside one cluster. The moment a side effect leaves that boundary — a charge, an email, a row in another database — you are back to at-least-once. So I made consumers idempotent instead: exactly-once effects, not exactly-once delivery.”

1
Processed-event ledger. Each consumer records the event ids it has handled and drops repeats. Pruned on a schedule so it does not grow forever — an interviewer will ask about retention, so mention it before they do.
2
Natural idempotency where possible. A unique constraint on Payment.orderId makes a double charge impossible at the database level — belt and braces with the ledger.
3
State-machine idempotency. The illegal transition returns null, so a duplicate cannot advance an order twice even if both other layers were removed.
4
Ordering of the two. Mark-processed-first vs act-first is a real choice: Inventory marks first so a crash mid-handler cannot double-consume a reservation, and the sweeper covers the case where marking succeeded but the act did not.

Module 4

Read-then-write, and the bugs it hides

One shape causes most “impossible” production bugs. Interviewers probe for it because it is invisible under low load and inevitable under high.

The shape

1
Read a value.
2
Decide something based on it.
3
Write the result back.

Two copies running at once both complete step 1 before either reaches step 3. Both decide against the same stale value. Engineers call the window between the check and the act TOCTOU.

🎰
Why it survives testing

Under test there is one request at a time, so the window never opens. It appears first in production, at the worst moment — a flash sale, a retry storm — and presents as data that “cannot happen”: negative stock, two payments, two live tokens in one family.

Three fixes, and when each is right

🔐

Compare-and-set

UPDATE … WHERE status = <what I read>. Zero rows affected means you lost the race. Best when losing is legitimate and should be a silent no-op — exactly the saga case.

🔒

Pessimistic row lock

SELECT … FOR UPDATE serialises the readers. Best when contention is high and retrying is expensive — stock, balances, counters.

🧬

Atomic upsert with a version guard

ON CONFLICT DO UPDATE … WHERE EXCLUDED.version > version. One statement, no read at all. Best for projections applying out-of-order events.

🗣️
Say the isolation level out loud

“Postgres defaults to READ COMMITTED, so two transactions can both read the same row and neither sees the other until commit. SERIALIZABLE would catch it, but it costs retries under contention — I preferred a targeted CAS to a global isolation change.” That sentence tells an interviewer you know the tradeoff exists.

CAS, in the saga

CODE 
  // Compare-and-set: `expected` is the status we read above. A lost CAS means another
  // event legitimately advanced this order, so this one must emit nothing.
  const moved = await tx.setStatus(p.orderId, next, order.status);
  if (!moved) return "NO_OP";
WHAT TO SAY ABOUT IT

“The third argument is the guard.” The write only lands if the row still holds the status we based our decision on.

“Losing is not an error.” It means another event advanced the order first, legitimately — so we emit nothing rather than retrying, which would double-emit.

The follow-up: “is this reachable?” Honest answer: not today, because Payment emits one deterministic result per order and one consumer group processes a partition serially. It is defence against a future second producer — and I would rather have it than discover the gap during an incident.

The sharpest example: claim before you mint

Refresh-token rotation. Two concurrent rotations of the same token both read revokedAt === null. Without a claim, both mint — and a thief racing the honest client never trips reuse detection.

CODE 
  // Claim the row FIRST. Under READ COMMITTED two concurrent rotations of the same token
  // both read revokedAt === null; whichever revoke commits second matches zero rows. Without
  // this check both would mint, leaving two live tokens in one family — and a thief racing
  // the honest client would never trip reuse-detection, which is the whole point of the
  // mechanism. The loser rolls back (the caller throws) and gets a 401.
  const claimed = await tx.revokeOne(row.id, now, true);
  if (claimed === 0) return { outcome: "RACE", userId: row.userId };
WHY THIS IS AN INTERVIEW ANSWER

It is a race with a security consequence, not just a data one. That distinction is what makes it memorable to an interviewer.

The order of operations carries the whole fix: revoke first, mint second. Reversed, the mechanism silently stops detecting theft while every test still passes.

The return value is the race detector. revokeOne returns rows affected — zero means someone else claimed it, so this caller must fail rather than proceed.

Volunteer the tradeoff: a 10-second grace window treats an honest double-submit from two tabs as legitimate instead of logging the real user out. It deliberately narrows detection by ten seconds.

services/identity/src/sessions.ts Rotation, family-scoped reuse detection, grace window — a pure function over a tx port.

Module 5

The edge: tokens, trust, and two bugs that nearly shipped

Auth questions reward precision. “We use JWTs” is a non-answer; the interesting part is what happens when one is stolen.

Two tokens, two jobs

🎫

Access token — 15 minutes

RS256 JWT, verified by the gateway with Identity’s public key. Fast, stateless, and impossible to revoke — which is exactly why it is short-lived.

🔑

Refresh token — 7 days

Opaque, not a JWT. Stored as a sha256 hash so a database leak yields nothing usable. Revocable, because it is a row.

🎯
The answer that shows you have thought about it

“Asymmetric signing means only Identity can mint a token, but every service can verify one — no shared secret to leak. The gateway fetches the public keys from a JWKS endpoint and picks by kid, so keys rotate without redeploying anything. It keeps the last good set if a fetch returns malformed JSON, because a bad deploy upstream should not lock every user out.”

“What if a refresh token is stolen?”

This is the question. Rotation alone is not an answer — rotation plus reuse detection is.

Step through the theft scenario
🔍
Why family-scoped, not user-scoped

Revoking every session for the user would log them out of their phone because their laptop was compromised — punishing the victim on every device. One chain, one family, one blast radius.

The gateway’s five jobs

strip, then inject Inbound x-user-id headers are removed unconditionally before verified ones are added. Otherwise anyone could claim to be anyone — and downstream services trust that header completely.
httpOnly cookies + double-submit CSRF The JWT never touches JavaScript, so XSS cannot read it. A readable CSRF cookie must be echoed in a header — an attacker’s site can send the cookie but cannot read it to set the header.
authz from a cached snapshot Permissions are a TTL-cached table, not a call per request. The cost is staleness bounded by the TTL, which you should state as a number.
circuit breaker per upstream One breaker per service, not per mount — so /products failing tells /comments nothing. Open circuit answers 503 immediately instead of queueing.
SSE exempt from the breaker A timeout would kill a healthy long-lived stream after seconds. Knowing which traffic must bypass your own resilience machinery is a senior-level detail.

Two bugs a review caught — both worth telling

🔓
Case-varied paths bypassed authentication. The rules table matched /products case-sensitively, but Express matches mounts case-insensitively and the upstream services did too. So POST /Products skipped both the permission check and authentication while still reaching Catalog. Fixed with case-insensitive patterns plus case sensitive routing at the app level — two layers, because one of them is a table a human maintains.
🚧
A proxy library upgrade silently broke every route. http-proxy-middleware v3 dropped the legacy req.url = req.originalUrl patch, so every app.use()-mounted route forwarded the mount-stripped path — the upstream saw /abc instead of /orders/abc and 404’d the entire proxied surface. The test suite was green because the stub had been written to match the broken shape. Tests now assert the exact upstream path.
💬
How to tell the second one

“The lesson was not about that library. It was that my test asserted against a stub I had written to match my own assumption — so it could only ever confirm it. Now the assertion is on the exact path the upstream receives, which is a fact about the contract rather than about my mental model.”

Module 6

The behavioural round, with receipts

“Tell me about a hard bug” is a test of how you think, not what broke. Each story below has the same shape: symptom, wrong hypothesis, what proved it, what changed permanently.

The shape of a good answer

S
Symptom — what a user or a graph actually showed. Not the cause; you did not know it yet.
H
Hypothesis you rejected — this is the part that signals seniority. Anyone can narrate a fix; naming what you ruled out and how shows method.
E
Evidence — the specific observation that settled it. A log line, a metric, a byte count.
C
Change that outlives the fix — the test, the alert, the rule. A story that ends at “then I fixed it” ends one beat early.

Story 1 — “every test passed and the feature did nothing”

THE INCIDENT 
// Distributed tracing shipped. Six tests, all green.
// Jaeger showed nothing at all.

// The SDK guard was keyed on process.env — which is
// INHERITED at spawn. tsx respawns into a child, so the
// parent started the SDK and the child — where the app
// actually runs — skipped it.
HOW TO TELL IT

Symptom: “Tracing was merged, tests green, and Jaeger had no spans.”

Rejected: “I assumed a collector or sampling misconfiguration and spent time there. Wrong — the SDK was never running in the process that mattered.”

Evidence: “The acceptance check we were using — ‘the SDK logs exactly once’ — was the signature of the bug. It logged once because only the parent ran it.”

Change: “Every test in that area now has to fail when the wiring is removed. Six plan-supplied tests would have passed against a broken implementation; that rule is what surfaced them.”

Five more, compressed

🧊
“Works locally, frozen in production.” A live stream advanced perfectly in dev and never moved behind nginx. Cause: proxy_buffering is on by default — sensible for a page, fatal for a stream. Lesson to state: the packaged shape has failure modes the dev shape cannot have, so it needs its own acceptance run.
📦
“Correct code, 404 in production.” A new endpoint worked in tests and 404’d through the gateway. The running container predated the route. Lesson: first question in any works-here-not-there bug is whether the running artifact contains the change.
🎲
“A flaky test that was not flaky.” Two browser walks failed intermittently and always at the same click. Not randomness — they were racing an asynchronous read-model projection, and a correct 422 came back. Lesson: intermittent plus always-the-same-place means a race, and a race has a signal you can wait on instead of a sleep.
🗑️
“A recovery tool that destroyed data.” The dead-letter replay used a no-ack read: a crash between reading and republishing destroyed the only copy of a message that could not be regenerated. Fixed to ack only after the publish confirms. Lesson: recovery paths need the same durability review as the write path — they run precisely when things are already broken.
🤫
“CI was green and doing nothing.” A shell loop used if ! case … esac; then, and POSIX suspends errexit inside a condition context — so a failed migration no longer aborted the job. Lesson: `set -e` is not a guarantee; verify by making a step fail on purpose and watching the pipeline go red.
🧵
The thread through all six

Every one was found by running the system — in a browser, in the packaged build, against real infrastructure — and every one had a green test suite over it. If you take a single sentence into an interview from this course, take that one.

“How do you know it works?”

The question that separates people who shipped from people who coded. Four layers, each answering a different question.

📊

SLOs with real numbers

Saga p99 < 5s, HTTP p95 < 500ms — expressed as k6 thresholds, so a load run exits non-zero when the objective is missed.

🔥

Burn-rate alerts

Alert on the burn rate of error budget consumption, not on raw error count — which is what stops a 3am page for a one-minute blip.

💣

Chaos scenarios

Kill a broker, kill a service, publish a poison message — then assert the system converges and the right alert fires.

✅

Invariant checker

Six properties across seven databases and both brokers — no order stuck non-terminal, no unsent outbox row, no reservation both consumed and released. Exit code, not a dashboard.

💡
The finding worth quoting

“Latency alerts do not catch hard outages. An open circuit answers in single-digit milliseconds, so during a chaos run availability collapsed while the latency alert never fired. Availability and latency need separate alerts — I found that by breaking the system on purpose, not by reasoning about it.”

The vocabulary sheet

Use these words precisely. Precision is most of what “senior” sounds like.

saga · compensating action Local steps with inverses, standing in for a transaction that cannot exist. Not “rollback”.
choreography vs orchestration React to events vs be told what to do. This system: choreographed execution, centralised state machine.
dual-write problem · transactional outbox Two systems, one commit needed. Turns atomicity into delivery.
at-least-once · idempotent consumer The realistic delivery guarantee, and the property that makes it safe. Exactly-once effects, not delivery.
TOCTOU · compare-and-set · SELECT FOR UPDATE The race, the optimistic fix, the pessimistic fix.
READ COMMITTED Postgres’s default, and the reason two readers can both see a stale row.
refresh rotation · reuse detection · family Rotate, detect replay of a rotated token, revoke one chain rather than one user.
JWKS · kid Publish public keys, select by key id, rotate without redeploying verifiers.
circuit breaker · back-pressure · DLQ Stop calling the dead, limit what you accept, park what you cannot process.
SLO · error budget · burn rate The target, the allowance, and the speed you are spending it — alert on the third.
read model · projection · eventual consistency A local copy fed by events, and the gap you must design around rather than wish away.

Final rehearsal

Pick any three terms above and explain each in two sentences: what it is, and what it costs. If the second sentence is hard, that is the topic to revisit — an interviewer will find it before you do.
